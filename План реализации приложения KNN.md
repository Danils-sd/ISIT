# План реализации приложения для определения типа телефона

Дата составления плана: 14 сентября 2026 года

## 1. Цель приложения

Приложение должно по ответам пользователя на вопросы из `Пр1.docx` определить, к какому классу он относится: `iPhone` или `Android`.

Для классификации используется метод k ближайших соседей (KNN). Обучающие примеры уже находятся в `dataset_normalized.csv`. При запуске приложение загружает эти примеры, использует столбец `phone` как целевую метку и после прохождения анкеты выдаёт прогноз.

Последний вопрос из документа — «У тебя айфон или андроид?» — не должен отображаться пользователю. Это целевой ответ для обучающих строк, а не вопрос пользовательского сценария. Ответ нового пользователя в текущей версии не добавляется в обучающую выборку и не используется для переобучения.

## 2. Что задано источниками и что задано пользователем

### Из учебного задания и PDF

- требуется применить метод k ближайших соседей;
- необходимо подготовить исходные данные;
- нужно протестировать решение;
- требуется сравнить разные значения `k` и объяснить, какое лучше;
- предусмотрены показ решения и code review другой команды.

### Из `Пр1.docx`

Документ задаёт порядок и формулировки вопросов. В нём 17 вопросов:

- вопросы 1–15 относятся к данным пользователя;
- вопрос 16 — цвет глаз;
- вопрос 17 — целевая метка «айфон или андроид».

В документе также есть вопрос о ближайшей станции метро. Он является обычным вопросом анкеты, но его признака нет в текущем CSV.

### Из `dataset_normalized.csv`

Фактическое содержимое датасета:

- 44 строки;
- 21 столбец;
- все значения числовые;
- пропущенных значений нет;
- полных дубликатов строк нет;
- признаки находятся в диапазоне от 0 до 1;
- `phone` содержит два значения: 0 и 1;
- распределение меток: 16 строк одного класса и 28 строк другого;
- цвет глаз представлен шестью one-hot-признаками;
- столбец `phone` физически находится не в конце таблицы, поэтому его нужно искать по имени, а не считать последним столбцом.

### Из требований пользователя

- вопросы показываются по одному, в заданном порядке;
- пользователь отвечает на каждый отображаемый вопрос;
- последний вопрос не показывается;
- после анкеты показывается результат: Android или iPhone;
- число `K` должно быть вынесено в константу;
- проверка качества должна находиться в отдельном модуле.

## 3. Несоответствия и зафиксированные решения

### Отсутствует вопрос о станции метро

В `Пр1.docx` есть вопрос о ближайшей станции метро, но в CSV нет столбцов для этого признака. Поэтому текущая модель не может использовать ответ на этот вопрос.

Рекомендуемое решение для первой версии — не показывать вопрос о метро и использовать только вопросы, представленные в CSV. В этом случае приложение будет показывать 15 вопросов, соответствующих 14 бинарным или числовым признакам и цвету глаз.

Альтернативный вариант — расширить датасет one-hot-признаками станций метро и заново проверить модель. При 44 строках и большом количестве станций это может привести к слишком разреженным и плохо обобщающимся признакам.

### Подтверждено соответствие меток и кодировок

По указанию пользователя и по сравнению с исходным файлом ответов `ИСИТ_1_практика_Ответы_на_форму_1.csv` установлено: `0` соответствует iPhone, `1` соответствует Android.

Сопоставление вариантов ответов с бинарными признаками также подтверждено сравнением исходных и нормализованных строк. Для интерфейса нужно сохранить это сопоставление в одном модуле, чтобы ответы пользователя преобразовывались так же, как обучающие данные.

Нужно также зафиксировать нормализацию двух числовых признаков:

- `phone_change_years` — количество лет до значения от 0 до 1;
- `games_hours` — количество часов в неделю до значения от 0 до 1.

Для приложения составляется словарь признаков: вопрос, варианты ответа, тип ввода, столбец CSV и правило преобразования в значение признака. Это предотвращает расхождение между ответами интерфейса и обучающей выборкой.

## 4. Предлагаемая архитектура

Jupyter следует использовать для исследования, графиков и проверки качества. Само пользовательское приложение должно запускаться как обычная Python-программа.

Для простой настольной формы предлагается использовать Tkinter: он входит в стандартную поставку Python и не требует отдельного сложного UI-фреймворка. Если понадобится только демонстрация в терминале, тот же слой модели можно подключить к консольному интерфейсу.

Предлагаемая структура проекта:

```text
app.py                  запуск пользовательского приложения
config.py               константа K и настройки меток
questionnaire.py        порядок вопросов и варианты ответов
preprocessing.py        преобразование ответов в признаки
knn_model.py            модель k ближайших соседей
data_validation.py      проверка структуры и значений датасета
quality_check.py        отдельная проверка качества
notebooks/              исследование в Jupyter
data/                   рабочая копия датасета
tests/                  тесты алгоритма и сценария анкеты
README.md               инструкция по запуску и описание решения
```

## 5. Логика запуска приложения

### Подготовка при старте

1. Приложение проверяет наличие CSV.
2. Проверяет обязательные столбцы, отсутствие пропусков, бинарность меток и корректность диапазонов.
3. Находит целевой столбец `phone` по имени.
4. Формирует матрицу признаков без `phone`.
5. Загружает обучающие данные и создаёт модель KNN.
6. Использует значение `K` из `config.py`.
7. Загружает описание видимых вопросов в порядке из `Пр1.docx`.

### Пользовательский сценарий

1. На экране отображается только один вопрос.
2. Пользователь выбирает вариант или вводит число.
3. Приложение проверяет, что ответ допустим.
4. После нажатия «Далее» текущий ответ сохраняется, а предыдущий вопрос заменяется следующим.
5. Целевой вопрос `phone` никогда не отображается.
6. После последнего доступного вопроса приложение собирает все ответы в один вектор.
7. Вектор преобразуется теми же правилами, что и обучающие данные.
8. Модель KNN вычисляет прогноз.
9. Числовой прогноз переводится в понятную подпись `iPhone` или `Android`.
10. Пользователю показывается результат и предлагается начать анкету заново.

На каждом шаге нельзя позволять перейти дальше с пустым или некорректным ответом. При этом приложение не должно добавлять ответ пользователя в обучающий CSV без отдельного требования на онлайн-обучение.

## 6. Обработка конкретных типов вопросов

- Бинарные вопросы отображаются двумя понятными вариантами, а не числами 0 и 1.
- Числовой ответ о сроке замены телефона принимается как целое число лет и нормализуется по подтверждённому правилу датасета.
- Числовой ответ об играх принимается как целое число часов в неделю и также нормализуется по подтверждённому правилу.
- Цвет глаз отображается выпадающим списком. Выбранное значение превращается ровно в один из шести one-hot-признаков.
- Вопрос о метро либо исключается вместе с соответствующим пояснением, либо добавляется в датасет до начала реализации. Показывать его и затем игнорировать в классификации не следует.

## 7. Модель и константа K

Для учебной прозрачности основной вариант — небольшая собственная реализация KNN: хранение обучающих векторов, вычисление евклидова расстояния, выбор ближайших соседей и голосование.

Готовый `KNeighborsClassifier` из `scikit-learn` можно использовать как контрольную реализацию. Совпадение результатов двух реализаций будет дополнительной проверкой правильности.

Значение `K` хранится в одном месте, например в `config.py`. В остальных модулях не должно быть разбросанных числовых значений соседей.

Итоговое значение `K` не следует выбирать заранее. Сначала модуль проверки качества сравнит несколько допустимых нечётных значений, после чего выбранное значение будет записано в константу приложения.

Так как текущий CSV уже нормализован и все признаки находятся в диапазоне 0–1, приложение должно использовать те же правила нормализации. Нельзя отдельно и иначе преобразовывать ответы пользователя: это нарушит сопоставимость расстояний.

## 8. Отдельный модуль проверки качества

`quality_check.py` не должен зависеть от UI и не должен запускаться при каждом ответе пользователя. Его задача — отдельно оценить подготовленные данные и модель.

### Проверка данных

Модуль проверяет:

- наличие ожидаемых столбцов;
- отсутствие `phone` среди входных признаков;
- отсутствие пропусков;
- допустимые диапазоны чисел;
- наличие ровно одной категории цвета глаз в каждой строке;
- бинарность целевой метки;
- баланс классов;
- соответствие количества признаков в CSV и вектора, который создаёт анкета.

### Проверка алгоритма

Нужно подготовить маленькие искусственные примеры, для которых ответ заранее известен:

- один очевидно ближайший сосед;
- большинство соседей одного класса;
- равное количество голосов;
- одинаковые расстояния;
- `K`, больший размера обучающей выборки;
- проверка детерминированного правила разрешения ничьей.

### Оценка на реальных данных

1. Данные разделяются стратифицированно, чтобы обе метки присутствовали в каждом разбиении.
2. Значения `K` сравниваются на обучающей части с помощью кросс-валидации.
3. Для каждого `K` сохраняются среднее качество и разброс между разбиениями.
4. Выбранное `K` проверяется на отложенных данных, если размер выборки позволяет сделать устойчивое тестовое разбиение.
5. Результат сравнивается с базовым прогнозом, который всегда выбирает самый частый класс.

Нужно вывести как минимум accuracy, precision, recall, F1-score и матрицу ошибок. При текущем дисбалансе классов дополнительно полезно показать balanced accuracy или macro F1.

При малом размере выборки основной вывод следует делать с учётом разброса результатов, а не по одному случайному разбиению.

## 9. Проверка пользовательского сценария

Помимо статистического качества модели, нужно проверить само приложение:

- при старте открывается первый вопрос;
- одновременно виден только один вопрос;
- вопросы идут в правильном порядке;
- целевой вопрос «У тебя айфон или андроид?» не показывается;
- вопрос о метро обрабатывается в соответствии с выбранным решением;
- нельзя перейти дальше без корректного ответа;
- после последнего видимого вопроса появляется ровно один итоговый прогноз;
- подписи Android и iPhone правильно соответствуют значениям 0 и 1;
- повторный запуск анкеты очищает предыдущие ответы;
- приложение использует тот же порядок признаков, что и модель.

Для интеграционной проверки можно взять существующую строку датасета, скрыть её целевую метку, подать остальные ответы через тот же преобразователь, что используется интерфейсом, и убедиться, что приложение получает предсказание без ошибки размерности или порядка признаков.

## 10. Проверка воспроизводимости

Перед демонстрацией нужно:

- запускать проверку из чистого окружения;
- выполнять Jupyter Notebook сверху вниз после перезапуска ядра;
- зафиксировать random seed для разбиений;
- сохранить список зависимостей;
- не хранить результаты, зависящие от случайного порядка запуска ячеек;
- описать запуск приложения и quality check в `README.md`.

## 11. Этапы работы

### Этап 1. Спецификация данных

Подтвердить соответствие 0/1 меткам телефона, правила нормализации числовых ответов и кодирование всех вариантов анкеты. Зафиксировать решение по вопросу о метро.

### Этап 2. Проверка CSV

Создать автоматическую проверку схемы, диапазонов, one-hot-цвета глаз, пропусков и баланса классов.

### Этап 3. Базовая модель

Реализовать KNN на подготовленных признаках и проверить его на искусственных примерах.

### Этап 4. Модуль качества

Добавить сравнение значений `K`, метрики, матрицу ошибок, базовый прогноз и проверку с помощью контрольной реализации.

### Этап 5. Пользовательское приложение

Собрать последовательную анкету, подключить единый преобразователь ответов и вывести итоговый прогноз.

### Этап 6. Интеграционная проверка

Сверить UI-вектор с вектором из CSV, проверить все переходы между вопросами и выполнить приложение с чистого запуска.

### Этап 7. Оформление и code review

Подготовить ноутбук с анализом, README с инструкциями, результаты выбора `K` и материалы для показа другой команде.

## 12. Критерии готовности

Работу можно считать выполненной, когда:

- приложение запускается без Jupyter как обычная Python-программа;
- все нужные вопросы показываются последовательно;
- целевой вопрос скрыт;
- ответ пользователя преобразуется в тот же формат, что и данные обучения;
- `K` хранится в единственной константе;
- модуль `quality_check.py` запускается отдельно;
- качество сравнивается для нескольких значений `K`;
- результат превышает или осмысленно сопоставляется с базовым прогнозом;
- отсутствует утечка столбца `phone` во входные признаки;
- проверены числовые, логические и интерфейсные ошибки;
- в отчёте честно описаны дисбаланс классов, малый размер выборки и отсутствие признака станции метро.

Главный риск проекта связан не с самим KNN, а с согласованием трёх вещей: порядка вопросов, кодирования ответов и порядка признаков в обучающем CSV. Поэтому именно их нужно зафиксировать первым шагом.
